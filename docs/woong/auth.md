# 회원가입·로그인·로그아웃·세션 작업 명세

- 담당: 웅싯 / 일정: D2 / 우선순위: P0
- 작업 브랜치: `feat/woong-auth`
- 대상: `/signup`, `/login`, 보호 경로 진입, 로그아웃
- 기준: 기능명세 1.1, 1주 개발 계획 2장·4.1·5.3·6.4

## 이용자 흐름

1. 비로그인 이용자가 이메일, 비밀번호, 닉네임을 입력하고 개인정보 수집·이용 동의를 확인한 뒤 가입한다. 약관·개인정보처리방침 링크와 만 14세 미만 가입 제한 안내를 제공한다.
2. `is_nickname_available`로 닉네임 중복을 확인하고 `supabase.auth.signUp`의 `options.data.nickname`으로 전달한다. 가입 트리거가 `profiles`를 생성한다. 이메일 인증 설정은 계획서의 1주차 결정에 맞추되, 실제 프로젝트 설정이 다른 경우 성공 안내에 인증 메일 확인 단계를 반영한다.
3. 기존 이용자는 이메일·비밀번호로 로그인한다. 보호 경로에서 온 경우 검증된 내부 `next` 경로로 복귀하고, 일반 로그인은 `/dashboard`로 이동한다.
4. 로그인 이용자는 로그아웃할 수 있고, 이후 보호 경로 진입 시 다시 로그인 화면으로 이동한다.

## 구현 작업

- [ ] 가입·로그인 화면에 필수값 검증, 제출 중 비활성, 성공·실패 알림, 모바일 키보드 사용성을 반영한다. 닉네임은 DB 규칙인 2~20자와 중복 여부를 확인한다.
- [ ] 잘못된 인증 정보, 이미 가입된 이메일, 닉네임 중복, 네트워크 오류를 사용자가 이해할 수 있는 문구로 표시한다. 서버 오류 원문이나 계정 정보는 노출하지 않는다.
- [ ] 기존 `lib/supabase/client.ts`, `server.ts`, `proxy.ts`를 재사용한다. 보호 경로는 `/dashboard`, `/attendance`, `/space`, `/me`, `/community`, `/groups`, `/dm`, `/mypage`, `/u`이며 공개 경로와 정적 파일은 통과한다. 세션 확인에는 `getClaims()` 또는 `getUser()`를 사용한다.
- [ ] 비로그인 보호 경로 요청을 `/login?next=<원래 내부 경로와 쿼리>`로 보낸다. 리다이렉트 시 갱신된 인증 쿠키를 보존하고, `next` 값은 같은 사이트의 상대 경로만 허용해 외부 URL 이동을 막는다.
- [ ] 가입·로그인 성공에 `signup_completed`, `login_completed` 이벤트를 각각 한 번 기록한다. 실패나 중복 제출은 성공 이벤트로 세지 않는다.
- [ ] `lib/supabase/proxy.ts`는 태일 소유 파일이므로 PR 설명에 변경 이유와 영향 범위를 명시한다.

## 완료·검수 기준

1. 정상 가입 → 로그인 → 보호 페이지 접근 → 로그아웃을 새로고침과 모바일·데스크톱에서 완료한다.
2. 잘못된 비밀번호, 중복 이메일, 중복 닉네임, 빈 필드, 네트워크 오류를 확인한다. 실패 후 입력값을 고쳐 재시도할 수 있다.
3. 비로그인으로 `/me/reading`, `/groups/123/chat` 같은 보호 URL에 직접 진입하면 로그인 후 원래 내부 경로로 돌아간다. 외부 `next` URL은 무시한다.
4. 다른 계정의 세션 쿠키나 UI 상태만으로 권한을 우회할 수 없다. 성공 이벤트가 `events`에 기록된다.
5. `npm run lint`, `npm run typecheck`, `npm run build`와 PR 프리뷰 확인을 완료한다.

## 의존성·PR 경계

태일이 만든 `profiles` 트리거·중복 닉네임 RPC·Supabase 클라이언트를 전제로 한다. 인증이나 RLS 변경이 포함되므로 태일 확인을 받은 뒤 머지한다. 소셜 로그인·비밀번호 재설정·결제는 이번 범위에 없다.
