## 1. 출시 범위 (1주에 맞춘 우선순위)

PRD 리스크 항목("2인 팀이 타이머·메타버스·메시징·모임을 동시에 만들면 일정이 늘어난다")에 따라, 명세서의 기능을 아래처럼 자른다.

### P0 — 반드시 출시 (D7에 없으면 출시 연기)

| 명세 | 기능 | 담당 | 1주 버전에서의 구현 수준 |
|---|---|---|---|
| 1.1 | 회원가입·로그인·로그아웃·세션 | 웅싯 | 이메일+비밀번호(Supabase Auth). 소셜 로그인 없음 |
| 1.2 | 마이페이지·프로필 수정·공개 프로필 | 웅싯 | 닉네임, 아바타 이미지, 한 줄 소개. 기록 원문은 노출 안 함 |
| 2.1 | 다도·독서 타이머 | 태일(제안) | 활동 유형 선택 → 시작 → 완료/중단. 동시에 1개만 실행 |
| 2.2 | 출석 상태 | 태일(제안) | 완료된 타이머가 하루 1건 이상이면 그날 출석(KST) |
| 3.1 | 독서기록 CRUD | 태일 | 목록·상세·작성·수정·삭제, 빈 상태 |
| 3.2 | 차 칼럼 CRUD | 태일 | 3.1과 같은 구조 + 제목 필드 |
| 6.1 | 커뮤니티 모임 탐색 | 태일 | 모임 목록·상세·생성·가입/탈퇴·관리(수정, 멤버 목록) |
| 6.2 | 모임 단체 채팅 | 웅싯 | 실시간 수신, 전송 중/성공/실패, 재시도, 중복 저장 방지 |
| 6.3 | DM | 웅싯 | 프로필에서 대화 시작, 대화 목록, 실시간 수신 |
| 7.1 | 반응형 웹 | 공동 | 360px 모바일 ~ 1440px 데스크톱 |

### P1 — 일정이 되면 출시 (없어도 출시는 함)

| 명세 | 기능 | 담당 | 1주 버전에서의 구현 수준 |
|---|---|---|---|
| 4.1 | 다도 입문 가이드 | 태일 | 저장소 안의 마크다운 5편 정도, 비로그인 열람 가능 |
| 5.1 | 메타버스 공간 | 태일 | 공용 공간 1개. 입장/퇴장 + "혼자 / N명과 함께" 표시. 아바타·이동 없음 |
| — | DM 차단 | 웅싯 | 차단한 상대는 DM 생성·전송 불가 (안전장치 최소선) |
| — | 랜딩 페이지 | 웅싯 | 흐름도의 "랜딩 페이지 → 로그인 여부" 단계 |

> 가이드와 메타버스는 명세상 중요도 🟡이라 P1로 두었다. 다만 둘 다 반나절 규모로 설계했으니, D5까지 P0가 계획대로면 같이 출시한다.

### 이번 출시에서 제외 (v1.1 이후)

- 플레이리스트 (저작권 문제로 PRD에서 보류)
- 모바일 앱, 소셜 로그인, 결제·구독
- 운영자 전용 관리 화면 → 출시 직후에는 **Supabase 대시보드로 운영**
- 신고 기능, 댓글·좋아요, 기록/칼럼 공개 기능, 아바타·공간 꾸미기, 메인 프로젝트 계정 연동

## 3. 기술 구성

### 3.1 스택

| 영역 | 선택 | 메모 |
|---|---|---|
| 프레임워크 | Next.js (App Router) + TypeScript | PRD 지정 |
| 스타일 | Tailwind CSS + 디자인 토큰(CSS 변수) | 컴포넌트는 직접 만들거나 shadcn/ui를 가져와 토큰으로 덮어씀 (웅싯 결정) |
| 인증 | Supabase Auth + `@supabase/ssr` | 미들웨어로 로그인 필요 경로 보호 |
| DB | Supabase Postgres + RLS | **모든 테이블 RLS 켬**. 예외 없음 |
| 실시간 | Supabase Realtime | 채팅·DM: Postgres Changes / 메타버스: Presence |
| 파일 | Supabase Storage | `avatars` 버킷만 사용 |
| 배포 | Vercel | PR마다 프리뷰 URL, `main` = 프로덕션 |
| 분석 | `events` 테이블 + `track()` 헬퍼 | 명세서의 "분석 이벤트 기록"을 한 곳으로 모음 |

### 3.2 라우트(화면) 지도 — 화면 흐름도 기준

| 경로 | 화면 | 로그인 | 담당 |

| `/` | 랜딩 (로그인 상태면 `/dashboard`로 이동) | — | 웅싯 |

| `/dashboard` | 타이머 대시보드 (메인), 출석 요약, 메타버스·가이드·개인페이지 진입점 | 필요 | 태일 |
| `/timer/[id]` 또는 대시보드 안 상태 | 타이머 실행 화면 | 필요 | 태일 |
| `/attendance` | 출석 상태 (달력/연속 출석) | 필요 | 태일 |
| `/space` | 메타버스 공간 | 필요 | 태일 |
| `/guide`, `/guide/[slug]` | 가이드 목록·상세 | **불필요** | 태일 |
| `/me` (개인 페이지) | 독서기록·차 칼럼 탭 | 필요 | 태일 |
| `/me/reading`, `/me/reading/new`, `/me/reading/[id]`, `/me/reading/[id]/edit` | 독서기록 | 필요 | 태일 |

| `/mypage`, `/mypage/edit` | 마이페이지·프로필 수정·로그아웃 | 필요 | 웅싯 |

### 3.3 데이터 모델 (D1에 태일이 첫 마이그레이션으로 만들고, 이후 각자 자기 테이블 추가)

| 테이블 | 주요 컬럼 | 소유 | 핵심 규칙 |
|---|---|---|---|
| `profiles` | `id`(=auth.users.id), `nickname` unique, `avatar_url`, `bio`, `created_at`, `updated_at` | 웅싯 | 가입 시 트리거로 자동 생성. 조회는 로그인 사용자 전체, 수정은 본인만 |
| `timer_sessions` | `id`, `user_id`, `activity`(`tea`/`reading`), `target_seconds`, `started_at`, `ended_at`, `status`(`running`/`completed`/`stopped`), `paused_at`, `paused_seconds` | 태일 | **`user_id` 기준 `status='running'` 부분 유니크 인덱스** → 중복 실행 DB에서 차단. 종료는 `where status='running'` 조건부 업데이트 → 중복 종료 방지 |
| (뷰) `attendance_days` | `user_id`, `day`(KST 날짜) | 태일 | `timer_sessions` 중 `completed`를 `(ended_at at time zone 'Asia/Seoul')::date`로 묶은 뷰. 별도 테이블 불필요 |
| `reading_logs` | `id`, `user_id`, `book_title`, `body`, `created_at`, `updated_at` | 태일 | 본인만 CRUD |
| `tea_columns` | `id`, `user_id`, `title`, `body`, `created_at`, `updated_at` | 태일 | 본인만 CRUD |
| `groups` | `id`, `name`, `description`, `owner_id`, `created_at` | 태일 | 조회: 로그인 전체 / 수정: 모임장 |
| `group_members` | `group_id`, `user_id`, `role`(`owner`/`member`), `joined_at` | 태일 | PK(`group_id`,`user_id`) |
| `group_messages` | `id`, `group_id`, `sender_id`, `body`, `client_id` unique, `created_at` | 웅싯 | 멤버만 조회·작성. `client_id`(클라이언트 생성 UUID)로 재시도 중복 저장 방지 |
| `dm_threads` | `id`, `user_a`, `user_b`, `created_at` | 웅싯 | `user_a < user_b` 체크 + unique(`user_a`,`user_b`) → 두 사람 사이 대화방 1개 |
| `dm_messages` | `id`, `thread_id`, `sender_id`, `body`, `client_id` unique, `created_at` | 웅싯 | 대화 참여자만 조회·작성 |
| `blocks` (P1) | `blocker_id`, `blocked_id` | 웅싯 | DM 생성·전송 RLS에서 확인 |
| `space_visits` | `id`, `user_id`, `space_id`, `entered_at`, `left_at` | 태일 | 분석용 기록. "지금 누가 있나"는 Realtime Presence로 판단 |
| `events` | `id`, `user_id`, `name`, `props` jsonb, `device`(`desktop`/`mobile`), `created_at` | 태일 | insert만 허용, 조회는 대시보드에서만 |
| 가이드 | 테이블 없음 → `content/guide/*.md` | 태일 | 비로그인 열람, 정적 생성 |

### 3.4 분석 이벤트 이름 (PRD 핵심 지표와 1:1로 맞춤)

`signup_completed`, `login_completed`, `profile_updated`, `timer_started`, `timer_completed`, `timer_stopped`, `attendance_viewed`, `reading_log_created`, `tea_column_created`, `guide_viewed`, `space_entered`, `space_left`, `space_avatar_updated`, `group_viewed`, `group_joined`, `group_message_sent`, `dm_started`, `dm_message_sent`, `post_created`

## 4. 역할별 상세 할 일

## 5. 비동기 협업 규칙

### 5.1 의존성 마감 (상대가 기다리는 것)

| 언제까지 | 누가 | 무엇을 | 누가 기다림 | 늦으면 |
|---|---|---|---|---|
| D1 종료 | 태일 | 저장소·로컬 실행·배포·`profiles` | 웅싯 D2 인증 | 웅싯은 디자인 시스템을 먼저 진행 |
| D1 종료 | 웅싯 | 디자인 토큰 + 대시보드 와이어 | 태일 D2 타이머 UI | 태일은 기본 스타일로 기능 먼저, D3에 스타일 입힘 |
| D2 종료 | 웅싯 | 기본 UI 컴포넌트 머지 | 태일 D3~ | 태일은 임시 마크업, 나중에 교체 |
| D3 종료 | 웅싯 | 커뮤니티·메타버스 시안 | 태일 D4~D5 | 태일은 와이어 수준으로 구현 |
| D3 종료 / D4 시작 | 태일 | `groups`·`group_members` 스키마 | 웅싯 D4 채팅 | 웅싯은 시드 데이터로 개발 |
| D3 종료 | 웅싯 | `/u/[id]` 공개 프로필 | 태일 D4 멤버 목록 링크 | 링크만 걸어 두고 나중에 연결 |

> 원칙: **기다리지 말고 목(mock)이나 시드 데이터로 먼저 진행**하고, 상대 결과물이 머지되면 교체한다.

### 5.2 데일리 비동기 로그 (작업 끝날 때마다 스레드에 남김)

```
[D? / 이름 / 작업 시간대]
✅ 한 일: (PR 링크)
➡️ 다음에 할 일:
⛔ 막힌 것:
🙋 상대에게 필요한 것: (없으면 "없음")
```

- 상대 작업을 시작하기 전에 **반드시 상대의 마지막 로그를 먼저 읽는다.**
- "🙋 상대에게 필요한 것"이 있으면 다음 작업 시작 시 가장 먼저 처리한다.

### 5.3 Git·코드 규칙

- 브랜치: `feat/<이름>-<기능>` (예: `feat/taeil-timer`, `feat/woong-chat`). `main` 직접 푸시 금지
- PR은 작게, 하루 1개 이상 머지. PR 설명에 프리뷰 URL과 확인 방법 적기
- 리뷰: 상대가 **12시간 안에** 리뷰. 넘기면 빌드·린트 통과 시 작성자가 머지해도 됨 (비동기라 리뷰 대기로 멈추지 않기 위함). 단 **마이그레이션·RLS·인증이 포함된 PR은 반드시 상대 확인 후 머지**
- 마이그레이션: `supabase/migrations/`에 타임스탬프 파일로만 추가. **이미 머지된 마이그레이션은 수정 금지**, 고칠 게 있으면 새 파일로. 만들기 전에 `main`을 먼저 pull
- 마이그레이션 머지 후 `types/database.ts` 재생성해서 같은 PR에 포함
- 공용 파일 소유자: `components/ui/`·전역 레이아웃 = 웅싯, `lib/supabase/`·`middleware.ts`·`lib/track.ts` = 태일. 상대 소유 파일을 고칠 때는 PR에 명시

### 5.5 교차 테스트 체크리스트 (D6)

- 가입(중복 이메일·닉네임) → 로그인 실패/성공 → 로그아웃 → 보호 경로 접근 시 로그인 유도
- 타이머: 시작 → 새로고침 → 다른 기기에서 열기 → 완료. 두 번 시작 시도. 완료 버튼 연타
- 출석: 완료 후 오늘 출석 표시, 중단만 한 날은 미출석, 자정 근처(KST) 기록
- 기록·칼럼: 작성·수정·삭제, 필수값 누락, 다른 계정으로 URL 직접 접근 시 차단
- 모임: 생성 → 다른 계정 가입 → 단체 채팅 양쪽 실시간 수신 → 탈퇴 후 채팅 접근 차단
- 채팅/DM: 네트워크 끊고 전송 → 실패 표시 → 재시도 → 중복 저장 없음
- DM: 프로필 → 대화 시작 → 같은 상대 재시작 시 기존 대화로 이동 → 차단 후 전송 거부
- 메타버스: 두 계정 동시 입장 → "함께" 표시 → 한쪽 탭 닫기 → "혼자"로 바뀜, 입장 중 타이머 정상
- 가이드: 로그아웃 상태 열람, 없는 주소
- 모바일: iOS Safari / Android Chrome에서 키보드가 채팅 입력창을 가리지 않는지, 하단 탭과 겹치지 않는지

## 6. 유의사항

### 6.1 일정·범위
1. **범위가 가장 큰 위험이다.** D5 기능 동결을 지키고, 새 아이디어는 "v1.1 백로그"에 적기만 한다.
2. 일정이 밀리면 자르는 순서: 메타버스 → 가이드 → DM 차단 → 모임 관리 페이지(수정만 남김) → 출석 달력(오늘 출석만 남김). **인증·타이머·기록·채팅은 자르지 않는다.**
3. D3 통합 #1에서 P0가 하루 이상 밀려 있으면, 그 자리에서 P1(가이드·메타버스) 제외를 결정한다.

### 6.2 기술
1. **타이머 시간은 클라이언트 `setInterval` 누적이 아니라 `started_at` 기준 계산.** 모바일 브라우저는 백그라운드에서 타이머를 멈추거나 늦춘다.
2. **출석은 KST 기준.** DB는 UTC로 저장하고 날짜로 묶을 때만 `Asia/Seoul`로 변환한다. Vercel 서버도 UTC라는 점 주의.
3. **중복 방지는 DB 제약으로.** 타이머 동시 실행(부분 유니크 인덱스), 종료 중복(조건부 업데이트), 메시지 중복(`client_id` unique), DM 방 중복(unique 쌍). 버튼 비활성화만으로는 부족하다.
4. Realtime 구독은 화면을 떠날 때 반드시 해제한다 (무료 플랜 동시 연결 수 제한, 메모리 누수).
5. `service_role` 키는 서버 전용. `NEXT_PUBLIC_`으로 시작하는 변수에 넣지 않는다.
6. 모바일 화면 높이는 `100vh` 대신 `100dvh`, 채팅 입력창은 키보드·하단 탭과 겹침 확인.

### 6.3 Supabase 운영
1. **기본 이메일 발송은 시간당 몇 통 수준으로 제한된다.** 이메일 인증을 켜 두면 출시 첫날 가입이 막힐 수 있다 → 2장 결정 #8대로 인증을 끄거나 커스텀 SMTP를 연결한다.
2. Auth의 Site URL·Redirect URL에 로컬, Vercel 프리뷰, 프로덕션 주소를 모두 등록한다.
3. 무료 플랜 프로젝트는 일정 기간 미사용 시 일시 정지된다. 출시 후 모니터링 담당을 정해 둔다.

### 6.4 개인정보·안전
1. 회원가입 화면에 개인정보 수집·이용 동의와 `/privacy` 링크를 둔다 (개인정보 보호법). 만 14세 미만 가입 제한 문구도 넣는다.
2. 공개 프로필에 독서기록·차 칼럼 원문이 절대 노출되지 않게 한다 (명세 1.2 비즈니스 규칙). 쿼리와 RLS 둘 다로 막는다.
3. DM은 신고 기능 없이 출시되므로 최소한 차단(P1)은 넣고, 문제 발생 시 Supabase 대시보드에서 계정 정지할 수 있게 절차를 README에 적어 둔다.
4. 아바타 업로드는 이미지 형식·용량을 제한하고, 버킷 경로를 `avatars/{user_id}/...`로 고정해 남의 경로에 쓰지 못하게 한다.

### 6.5 디자인·콘텐츠 저작권
1. getdesign.md 등 참고 자료는 구조만 참고하고, 색·레이아웃·일러스트를 그대로 가져오지 않는다 (PRD 차별점·리스크 항목).
2. 폰트·아이콘·일러스트는 상업 이용 가능한 라이선스만 쓴다 (예: Pretendard, Noto Sans/Serif KR, Lucide). 출처를 README에 남긴다.
3. 가이드 원고를 AI로 초안 작성했다면 사실 확인(차 종류별 물 온도 등)을 사람이 검수한다.
4. 플레이리스트·배경음악은 넣지 않는다.

### 6.6 메인 프로젝트 연계
- PRD의 "메인 프로젝트와의 연계"는 이번 1주 범위가 아니다. 다만 나중에 계정을 합칠 수 있도록 사용자 식별은 `auth.users.id`만 외래 키로 쓰고, 이메일·닉네임을 다른 테이블의 키로 쓰지 않는다.
